# Restate Operator v3.2.2 Release Notes

See the [v3.2.1 release notes](https://github.com/restatedev/restate-operator/blob/main/release-notes/v3.2.1.md) for changes prior to this release.

## Highlights

- **Canary Jobs use the cluster's image pull secrets.** The Pod Identity and Workload Identity canaries now pull their image with the secrets in `spec.compute.imagePullSecrets`, so a canary image from an authenticated registry no longer keeps the cluster from becoming Ready.
- **RestateDeployment retries back off against the admin API.** Failed admin API calls are retried after 30 seconds at first and up to 5 minutes later, with jitter, and each request times out after 120 seconds.

## Upgrade Notes

- No CRD changes. The image and both charts can be rolled without applying CRDs.
- On clusters that set `imagePullSecrets`, the existing canary Job is recreated once after the upgrade, and the cluster reports `NotReady` until the new canary succeeds.

## Bug Fixes

### Canary Jobs use the cluster's image pull secrets

#### What Changed
The Pod Identity and Workload Identity canary Jobs now use the image pull secrets listed in the RestateCluster's `spec.compute.imagePullSecrets`, the same ones the `restate` StatefulSet uses. Before, the canary pods had no pull secrets.

#### Why This Matters
When the canary image (`--canary-image`) is served by a registry that needs credentials, the canary pod stayed in `ImagePullBackOff`. The RestateCluster then never became Ready and the StatefulSet was never created, even though the Restate server image itself could be pulled with the named secret.

#### Impact on Users
- Clusters that name pull secrets and use Pod Identity or Workload Identity with a canary image from an authenticated registry now get past the canary.
- On clusters that set `imagePullSecrets`, the existing canary Job, stuck or already completed, is deleted and recreated with the pull secrets on the first reconcile after the upgrade. The cluster reports `NotReady` until the new canary succeeds.
- Clusters without `imagePullSecrets` see no change.

Related: #265.

## Behavioral Changes

### RestateDeployment retries back off against the admin API

#### What Changed
- When a RestateDeployment's calls to the Restate admin API fail or are rejected, the operator now retries after 30 seconds at first and backs off to 5 minutes the longer the failure lasts. It used to retry every 30 seconds indefinitely. Other reconcile failures, such as a missing Secret, still retry after about 30 seconds.
- Retry intervals and the routine 5-minute re-check of healthy deployments are jittered by up to 20%, so deployments on the same Restate cluster no longer call its admin API in lockstep.
- Admin API requests now time out after 120 seconds (10 seconds to connect). Before, a request to an unresponsive admin API could hold its reconcile indefinitely.
- A ReplicaSet without a status now reports `ReplicaSetNoStatus` as the `Ready` condition's reason; the reason and message were swapped.

#### Why This Matters
A Restate cluster that is struggling or unreachable was retried at a fixed rate by every RestateDeployment pointing at it, which adds load at the moment the cluster can least absorb it.

#### Impact on Users
- A deployment that has been failing for a while takes up to about 6 minutes to notice that the admin API has recovered, unless a change to the resource or its pods triggers a reconcile sooner.
- Pods that are still starting are not treated as failures and keep their existing re-check interval.
- While a RestateDeployment is being deleted, failed admin API calls back off by how long the deletion has been running.
- No manifest, Helm value, or migration change is required.
