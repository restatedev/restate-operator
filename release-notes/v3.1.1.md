# Restate Operator v3.1.1 Release Notes

See the [v3.1.0 release notes](https://github.com/restatedev/restate-operator/blob/main/release-notes/v3.1.0.md) for changes prior to this release.

## Highlights

- **Security: compromised eMudhra intermediate CAs are no longer trusted.** The same fix shipped in 2.7.2 and 2.8.2; this brings it to the 3.x line.
- **Helm: the old operator pod stops before the new one starts.** Upgrades no longer run two operator versions side by side.

## Bug Fixes

### Security: distrust compromised eMudhra intermediates

Eight eMudhra intermediate CA keys were compromised (RUSTSEC-2026-0381, RUSTSEC-2026-0382). They are cross-signed under Sectigo's AAA Certificate Services root, so removing the emSign root alone does not block them. `rustls-webpki` 0.103.16 blocks all eight by public key, whatever the root.

| Crate | From | To |
| --- | --- | --- |
| `rustls-webpki` | 0.103.13 | 0.103.16 |
| `webpki-roots` | 1.0.6 | 1.0.10 |
| `rustls` | 0.23.37 | 0.23.46 |
| `h2` | 0.4.13 | 0.4.20 |
| `anyhow` | 1.0.102 | 1.0.104 |

No configuration change and no CRD change.

Related: #222 (2.7.2: #223, 2.8.2: #224).

### Helm: no overlapping operator pods during an upgrade

#### What Changed

The chart now sets the operator Deployment's update strategy, configurable as `strategy`:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 0
    maxUnavailable: 1
```

Before, the Deployment used Kubernetes' default (25% surge), which starts the new operator pod while the old one is still running.

#### Why This Matters

The operator has no leader election. During an upgrade both versions reconciled the same resources for a while. When the two versions render a resource differently, each force-applies its own version in turn. Upgrading from 2.x to 3.x does this to every RestateCluster with `spec.security.requestSigningPrivateKey`, because 3.0 renamed the environment variable that points Restate at the key. In a test cluster the StatefulSet was rewritten about 200 times and the Restate pod restarted three times instead of once.

With `maxSurge: 0` the old pod receives SIGTERM first and finishes its in-flight reconciles before the new pod starts.

#### Impact on Users

- Upgrading to this chart already uses the new strategy, including from 2.x.
- An operator upgrade now has a few seconds in which no operator pod runs. Nothing is reconciled during that time; the new pod catches up when it starts.
- `replicaCount` above 1 is still not supported: without leader election, replicas reconcile concurrently.

#### Migration Guidance

None needed. To use `Recreate` instead, set `strategy.type=Recreate` and `strategy.rollingUpdate=null` on a fresh install. An existing Deployment cannot switch to `Recreate` through `helm upgrade` with server-side apply (the Helm 4 default): the API server keeps the defaulted `rollingUpdate` and rejects the change.
