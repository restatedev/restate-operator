# Restate Operator v3.2.1 Release Notes

See the [v3.2.0 release notes](https://github.com/restatedev/restate-operator/blob/main/release-notes/v3.2.0.md) for changes prior to this release.

## Highlights

- **The operator no longer re-triggers itself on its own status writes.** The RestateCluster watch is filtered, so a status update no longer causes another reconcile. This ends the self-sustaining reconcile storms seen after an operator restart on large fleets.
- **A storage change keeps the StatefulSet's update strategy.** When the operator recreates the `restate` StatefulSet for a storage change, the new one carries the old `updateStrategy` instead of falling back to `RollingUpdate`.

## Upgrade Notes

- No CRD changes. The image and both charts can be rolled without applying CRDs.
- The operator Docker image is now pinned to a specific `distroless` base and tracked by Dependabot.

## Bug Fixes

### Status writes no longer re-trigger RestateCluster reconciles

#### What Changed
The RestateCluster controller watched its own resource without a filter. Every reconcile ends in a status write, and that write came straight back as the next `object updated` trigger. The watch now goes through a filter that hashes only what the reconciler reads: the spec (generation), labels, annotations, finalizers, `deletionTimestamp` and `uid`. A status-only update is dropped; a spec change, the `restate.dev/reconcile` annotation, a finalizer add and a delete request still trigger a reconcile. The periodic requeue is unchanged.

#### Why This Matters
On a quiet cluster the loop only costs one wasted pass per reconcile. When the operator falls behind, for example right after a restart on a fleet of several hundred RestateClusters, the API server closes the watch for unresponsiveness, the re-watch replays every object, and the resulting wave of status writes fed the next wave. The operator then stayed pinned at its CPU limit, reconciling every cluster tens of times per second, for hours.

#### Impact on Users
- Existing deployments: reconciles that did no work disappear; the reconcile rate and log volume drop. No change to what the operator manages.
- New deployments: no change.

Related: #242.

### The StatefulSet update strategy survives a storage recreate

#### What Changed
A storage change makes the operator delete the `restate` StatefulSet with `Orphan` and create it again. The operator never sets `updateStrategy`, so the recreated StatefulSet came back as the default `RollingUpdate`, whatever the old one had. The operator now records the old strategy in the `restate.dev/recreate-update-strategy` annotation on the RestateCluster before the delete, waits for the old StatefulSet to be gone instead of applying to the terminating object, and recreates with that strategy under a second field manager, `restate-operator-update-strategy`, which owns only that field. The annotation is cleared afterwards.

#### Why This Matters
A graceful roll sets `OnDelete` so that each pod can be drained before it is deleted. If a storage change and a pod template change landed in the same reconcile, the recreated StatefulSet rolled every pod itself, with no drain.

#### Impact on Users
- StatefulSets with the default strategy: no change.
- StatefulSets with `OnDelete` (or any non-default strategy): it is kept across a storage change. The RestateCluster carries the `restate.dev/recreate-update-strategy` annotation while the recreate is in progress.

Related: #226.
